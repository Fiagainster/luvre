# ch20 复现手记 — 顺着正常人的路径解题

> 样本：`D:\临时取证\测试\ch20.bin`（732 B，ELF32 i386，Root-Me 系 crackme，strip）。
> 本文是给「照着复现」的操作手册：每一步点哪个按钮、输入什么、应该看到什么、
> **以及为什么这一步这么走**。所有按钮名、面板读数、字节数都是对着工具逐个核过的——
> 照着做如果对不上，先怀疑样本差异，再怀疑工具版本。
> 路径刻意按普通人的直觉排：字符串看起 → 能看伪代码绝不啃汇编 → 只在伪代码卡壳的
> 两处局部看汇编 → 算出答案 → 动态跑一遍盖章。
> 答案在 §7：**`HardW@re_Br3akPoiNT_r0ckS`**（先自己推，卡住再看）。
> 工具版本：v0.4.2+ 可走通全流程；HEX 工具栏按钮文案（⚗ 解码 等带字）、
> 裸反汇编地址列对齐、XOR 结果区关闭按钮是 v0.4.3 之后修的——旧版功能相同，
> 只是按钮是纯符号、要 hover 才知道是干嘛的。

## 0. 启动与打开

1. `python -m luvre`（或 `pip install luvre` 后 `lvr`）→ 浏览器自动开 `http://127.0.0.1:7331`
2. 点 **⌖ 打开二进制**，路径框输入 `D:\临时取证\测试\ch20.bin` → 回车
3. 等引擎分析完成。右侧「程序」面板：732 B / 基址 0x08048000 / **函数数 2**
   （`entry` 149 B + `FUN_08048115` 14 B——代码总共 163 字节，全在这两个函数里）

此时你**对这程序一无所知**，手里只有三份免费情报：

- **查壳 · 结论面板**（工具替你做的判断）：无壳、无附加数据、无密码学常量
  → 直接排除「脱壳题」和「crypto 签名题」两条路，省掉两轮试错
- **函数面板**：就 2 个函数、共 163 字节 → 程序很小，读得完
- **字符串面板**：下一步的主战场，见 §1——但它的真实输出和直觉不一样

## 1. 第一步永远是字符串（但要预期它给不全）

为什么先看字符串：**不用懂任何指令集、不用等反编译，30 秒拿到剧情大纲**。
这题字符串面板的真实输出是 **5 条**（底部状态栏「5 字符串」可对照），逐条列给你：

| 地址 | 内容 | 情报价值 |
|---|---|---|
| 0x80491a1 | `Welcome to Root-Me Challenges\r\nPass: ` | ★ 唯一的真台词：程序会**主动提示输入**——存在一条「输入 → 校验」主线 |
| 0x1 | `.shstrtab` | 垃圾：节名表被当成字符串了 |
| 0xb | `.text` | 垃圾 |
| 0x11 | `.data` | 垃圾 |
| 0x17 | `.note.gnu.gold-version` | 垃圾（链接器痕迹） |

注意那 4 条垃圾的地址是 0x1、0xb 这种小得离谱的值——那是节名表内部的偏移，
不是内存地址，直接无视。

**关键教训：面板只报 Ghidra「认出来」的字符串，不是程序的全部字符串。**
为什么两句最关键的台词（成功/失败回执）没被认出来？看 §5 的 `.data` 实测布局就懂了：
Ghidra 的字符串识别靠 **NUL 终结符**收尾——banner 结尾恰好有 `\x00`，认出来了；
而「Well done…flag!\n」和「Try again!\n」背靠背、中间没有 NUL，启发式认不出边界。
手写汇编的 crackme 没有节表标注，这种情况很常见。

所以 §1 的正确姿势是：**从 banner 读出「有输入主线」这个判断就够了，台词没给全不要恋战**。
缺失的情报会在 §3（裸反汇编的 write 参数里）和 §5（HEX 面板）补回来。
题型判断到此已经成立：**比较型 crackme**（给输入 → 和某个东西比 → 成功/失败）。

## 2. 第二步看伪代码（能看图绝不啃汇编）

center 面板双击 `entry` → ✎ 伪代码。**这一步的收获比想象的大**——校验主干其实直接读懂了。
真实反编译输出如下（Ghidra 12.2）：

```c
void processEntry entry(void)
{
  ...
  pcVar1 = (code *)swi(0x80);  (*pcVar1)();   // ← 五个 syscall 长得一模一样
  pcVar1 = (code *)swi(0x80);  (*pcVar1)();
  FUN_08048115();                              // ← 种子从这里来？
  iVar3 = 0x19;                                // j = 25
  uVar4 = extraout_ECX;                        // ← 种子悬空：寄存器返回值
  do {
    uVar2 = uVar4 >> 1;                        // 每轮右旋 1 位
    uVar4 = uVar2 | (uint)((uVar4 & 1) != 0) << 0x1f;
    if ((*(byte *)(iVar3 + 0x8049154)          // A[j]
         ^ *(byte *)(iVar3 + 0x8049187))       // input[j]
        != (byte)uVar2) {                      // 三方异或不等 → 失败
      ... goto 失败出口
    }
    iVar3 = iVar3 + -1;
  } while (iVar3 != 0);
  ... 成功出口
}
```

从伪代码**直接读到的**（本题的大半逻辑，不需要任何汇编）：

- 校验循环：j 从 25 数到 1，每轮把某个 32 位值右旋 1 位，
  比较 `A[j] ^ input[j]` 是否等于旋出的低 8 位——**异或消去就能直推输入**，无需反演
- 数据地址：A 表基址 `0x8049154`、输入缓冲基址 `0x8049187`、循环 25 轮 → **密码 25 字符**
- 一个容易疑惑的细节：伪代码里是 `iVar3 + 0x8049154` 且 j 从 25 起算——这是 **1-based 下标**，
  有效字节范围 0x8049155..0x8049169，所以 §5 里 A 表第一个字节在 **0x8049155**
  （0x8049154 本身是上一句台词的换行符）。input 同理（0x8049187+j → 实际缓冲从 0x8049188 起）。

伪代码**给不了的**（这才是卡壳点，注意只有两处、都很局部）：

1. **五个 `swi(0x80)` 一模一样**：syscall 号（eax）和参数（ebx/ecx/edx）全被反编译器吞掉，
   分不清哪句是打印提示、哪句是读输入、哪句是退出。连最后的 `exit(0)` 都被还原成
   一个空转 do-while——手写汇编没有函数原型，反编译器只能瞎猜。
2. **种子来源断了**：`extraout_ECX` 是悬空的寄存器返回值；点开 `FUN_08048115` 的伪代码，
   只看到一个「空转减法循环」——**真正的哈希算法被整个吞掉了**（它写入的是子寄存器 cl，
   Ghidra 对无原型手写汇编的子寄存器返回值还原经常失败）。

## 3. 卡壳点一：给五个 int 0x80 认参数（局部看汇编，30 秒）

只为了分清五条 syscall，不需要通读。切 ⚡ 裸反汇编（或 entry 的汇编视图），地址 0x08048080。
看每条 `int 0x80` **前面**的寄存器赋值即可——i386 Linux 的规矩：eax=系统调用号，
ebx/ecx/edx 是参数：

| 位置 | eax | 含义 | 翻译 |
|---|---|---|---|
| 0x08048080 | 4 | write | 打印 banner（0x80491a1，38 字节）——正是 §1 那句真台词 |
| 0x08048096 | 3 | read | **读 51 字节到 0x8049188** ← 输入缓冲（与伪代码 input 侧 0x8049187+1 对上） |
| 0x080480de | 4 | write | 成功回执（**0x8049124**）——§1 缺的台词之一，地址在这露脸 |
| 0x080480f6 | 4 | write | 失败回执（**0x804914a**）——另一句 |
| 0x0804810c | 1 | exit | 退出 |

§1 没看到的两句台词到这里就找齐了：地址在 write 的参数（ecx 立即数）里，
拿去 HEX 面板读内容（§5）。**「字符串面板没给全」从来不是死路——立即数里全是情报。**

顺手确认了 call 前的送参（0x080480a9）：`eax=0x08048080, ebx=0x8048123, ecx=0`
→ 告诉哈希函数「对 0x08048080–0x08048123 这段做处理」——**这段是程序自己的代码**，
共 163 字节。到这里伪代码的悬空点 1 补完，校验循环的语义完整了；悬空点 2 见下一步。

## 4. 卡壳点二：FUN_08048115 到底干了什么（14 字节定乾坤）

伪代码说它「啥都没干」，汇编只有 7 条指令：

```asm
0x08048115  sub  ebx, eax        ; 计数 = 终点 - 起点 = 163 字节
            xor  ecx, ecx        ; 累加器清零
0x08048119  add  cl, [eax]       ; 低 8 位吸收一个代码字节
            rol  ecx, 3          ; ★ 整个 32 位 ECX 左旋 3 位
            inc  eax / dec ebx
            jne  0x08048119      ; 循环 163 次
            ret                  ; 种子留在 ECX 里返回
```

翻译成人话：**把程序自身的 163 字节代码滚一遍哈希**——低 8 位吃进一个字节、
全寄存器左旋 3 位，163 次后 ECX 里就是校验循环用的种子。
伪代码吞掉的恰好是 `add cl` + `rol ecx,3` 这两行关键动作，所以必须看这 14 字节。

### 死坑：假种子 0x3C283DD3

第一版模拟把 `cl` 写成独立累加器（`cl = (cl+b) & 0xFF` 带出循环），
算出 seed = 0x3C283DD3，密码全是乱码。错在哪：

- `add cl,[eax]` 只改 ECX 的**低 8 位**，但上一轮 `rol ecx,3` 已经把高位绕回了低位——
  低 8 位里躺着历史高位，**不能脱离 S 单独累加**；
- 正确做法每轮从当前 S 取低 8 位再加字节（§7 脚本的 `lo` 行）。

> 经验：模拟寄存器哈希时，先问「这个 8 位子寄存器是不是全寄存器的投影」——
> rol/ror 之后 `cl/ch/dl` 全都混进了别处的位，独立维护必错。

## 5. HEX 面板把数据读齐

切 ⊞ 内存 HEX，跳转框输地址回车（合法绝对地址自动定位所在块；乱填会得到
列出可读范围的 toast，不再发注定失败的请求）。`.data` 块从 0x8049124 到 0x80491C7，
实测布局一张表：

| 地址 | 内容 | 怎么用 |
|---|---|---|
| 0x8049124 | `Well done man, use this pass to flag!\n`（38 B） | §3 成功回执归位 |
| 0x804914A | `Try again!\n`（11 B） | §3 失败回执归位 |
| **0x8049155** | **A 表 25 字节**：`1e cd 2a d5 34 87 fc 78 64 35 9d ec de 15 ac 97 99 af 96 da 79 26 4f 32 e0` | ★ 推密码的唯一外部数据 |
| 0x8049170 前后 | 填充（一串空格 + \n + NUL） | 无用，跳过 |
| 0x8049188 | 输入缓冲区（read 的 51 字节，密码占前 25） | 只在动态调试时有用 |
| 0x80491A1 | banner（结尾带 `\x00`——§1 里它为何被认出来的答案） | 对照 |

注意两个坑：

- **A 表起点是 0x8049155 不是 0x8049154**——0x8049154 上是 `Try again!\n` 的换行符（0a）。
  跳 0x8049154 看到行首一个 `0a` 别慌，往后一个字节才是 A[1]。
  （§2 说过：伪代码用 1-based 下标，`0x8049154 + j` 的最小有效 j 是 1。）
- 单页只有一块的量，地址跳到位即可；要整块连续读用块下拉框选 `.data`。

## 6. 拿全 163 字节代码 → 解码实验室

自哈希种子要 163 字节代码原文（§4 已确认哈希对象是代码自身）。
代码在 `.text` 块（0x08048080 起，恰好 163 B），运气好：**一页就能拿满，连 Shift 都不用按**。

1. ⊞ 内存 HEX 页签，块下拉框选 **`.text`** 点 ◂ 上一页/读取，或跳转框输 `0x08048080` 回车
   ——两法等价，都落到 .text 整块
2. 点工具栏上的 **「⚗ 解码」** 按钮（v0.4.3 之后带文字；更早版本是纯 ⚗ 符号，
   hover 才显示「把当前块字节送入解码实验室」）→ 右下解码实验室被唤起，
   输入框变成空格分隔的 hex 串，输入格式自动切到 **hex**，
   标签显示 **(163 bytes)** ← **这个数字就是你的核对点**
3. 核对首尾：开头 `b8 04 00 00`，结尾 `75 f7 c3`（§4 那两条指令的字节）
4. 全选输入框内容复制（Ctrl+A → Ctrl+C），存成文本文件备用

两个 footgun，都实测过：

- **跳 0x08048000 起读会把 ELF 头一起带回来**（128 B 头 + 163 B 代码 = 291 B 连续可读，
  标签会显示 (291 bytes)）。脚本会把多余的钳掉并警告，但最好直接从 `.text` 块读。
- **Shift+⚗ 解码 是给大块用的**：仅当当前页恰好满 4096 B（一页装不下）时，
  按住 Shift 点击会从当前偏移继续拉，最多 8 页 / 32 KB 自动拼接（toast 报总字节数）。
  ch20 的 163 B 一页拿满，按不按 Shift 结果一样。

## 7. 算种子、推密码（本地 Python 脚本）

旧版手册让人往浏览器 console 粘两段 JS——能跑但很蠢：粘错一个字符就静默算错、
没有断言、重算要重粘。所以这次直接给本地脚本
**`docs/scripts/solve_ch20.py`**（同仓库，纯标准库），
同样的两步算术，外加**校验循环回验**：把推出来的密码代回 crackme 的比对逻辑再跑一遍，
逐位通过才算数。

```bash
# 把 §6 复制的 hex 存成 code.txt（空格、换行、hexdump 地址列都能认），然后：
python docs/scripts/solve_ch20.py code.txt
```

预期输出（三行都要对上）：

```
[*] 代码字节：163 B（头 b8040000 尾 75f7c3）
[*] 自哈希种子 = 0xac77e166
[*] A 表：25 字节
[+] 密码（25 字符）：HardW@re_Br3akPoiNT_r0ckS
[+] CHECK PASS — 与 crackme 校验循环逐位一致
```

种子哈希的正确语义（对应 §4 的机器码）：

```
ECX = 0
对每个代码字节 b：低 8 位 = (当前 ECX 低 8 位 + b) & 0xFF   ← 只动低 8 位
                 ECX = rol32(ECX, 3)                        ← 整个寄存器旋转
```

- **种子 seed = 0xAC77E166**（163 字节代码自哈希，静态可复算）
- **密码 = `HardW@re_Br3akPoiNT_r0ckS`**（25 字符）
- 推导式：`input[j] = A[j] ^ low8(ror32(seed, 26−j))`，j = 1..25——§2 伪代码里
  「三方异或相等」的逆写：异或消去，input 就是 A 和旋位的异或
- 校验公式里 (26−j) 的来历：j=25 时第 1 次右旋（26−25=1），j=1 时已旋 25 次——
  伪代码每轮「先旋再比」的直译
- 脚本里那个 25 字节 A 表默认内置（就是 §5 抄的）；如果你算别的题，`--a` 换表、
  `--seed` 跳过哈希、`--len` 改长度，脚本通用
- 仓库里附了一份 `docs/scripts/ch20_code_hex.txt`（就是 §6 该拿到的 163 B），
  不开样本也能先验证脚本本身：`python docs/scripts/solve_ch20.py docs/scripts/ch20_code_hex.txt`

如果种子算出 **0x3C283DD3**，脚本会直接提醒：那是 §4 的假种子坑，
`add cl` 被当独立累加器了——回 §4 重看两行。

## 8. 动态验证只是盖章（静态已经出答案）

到这里答案已经算完了，跑一遍只是让程序自己承认。而且**动态排在最后是有意的**：
静态不用起 WSL、不用管断点时序，推错随时重算；动态是最后的裁判，用来排除
「静态推错/漏看」的可能，成本放最后。

1. 切 ⚙ 动态调试页签，选 WSL / Ubuntu-22.04（路径自动转 /mnt/d/...，控制台
   中文路径显示正常）
2. stdin 文本框填：`HardW@re_Br3akPoiNT_r0ckS`（结尾换行带上更稳——§3 已确认程序用
   裸 read 系统调用读 stdin；本桥把 stdin 落成临时文件做 `< 重定向`，read 一次拿满，
   不严格需要换行，但在真终端里手跑时行缓冲会等整行）
3. ▶ 启动会话 → ▶ 运行
4. 控制台依次出现 banner、`Well done man, use this pass to flag!`、`[Inferior 1 exited normally]`

> 对照组（顺手发现的邻题事实）：ch18.bin 在**任何输入**下都零输出——

> 别把「console 里没看到输出」当成工具回归，先 strace 一把再下结论。

## 9. 路径复盘（这次为什么这样走）

本题实际走的阶梯，每级都用更便宜的工具：

```
字符串（免费剧情，30 秒——但要预期它给不全）
  → 伪代码（免费主干——校验循环直接读懂，本题的大半）
    → 局部汇编（只补伪代码吞掉的两处：syscall 参数 5 行、哈希函数 14 字节）
      → HEX 读数据（A 表 25 字节）
        → 本地脚本（种子 + 密码 + 回验，纯算术）
          → 动态盖章（答案已经算完，跑一遍确认）
```

四条普适经验：

1. **「要看汇编了」的信号不是代码体积，是伪代码里的三类异常**：成排一模一样的
   `swi(0x80)`（syscall 参数被吞）、悬空的 `extraout_*` 寄存器（返回值走的是
   反编译器不认识的寄存器约定）、看起来「啥都没干」的小函数（子寄存器写入 +
   无函数原型，还原失败）。出现任意一个，就针对那**一小段**看汇编，而不是全篇切换。
2. **伪代码经常比你预期能扛更远**：本题校验循环的异或结构、轮数、数据地址全在
   伪代码里，密码推导式直接由它读出。汇编只负责「伪代码吞了什么」的补刀。
3. **字符串面板是索引不是全集**：它只报 Ghidra 认出来的（NUL 结尾、有干净边界的）。
   手写汇编题里关键台词经常背靠背没有终结符——漏了别恋战，§3 的 write 立即数
   和 §5 的 HEX 面板都是兜底。
4. **静态优先、动态收尾、中间用脚本不用 console**：静态推错立刻重算，动态起环境
   有固定成本；页内粘 JS 能跑但没法断言没法复用——同样的算术写成本地脚本，
   输入格式容错（纯 hex / 空格分隔 / hexdump 都认）、自带回验，重算成本趋近于零。
